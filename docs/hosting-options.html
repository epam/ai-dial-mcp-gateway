Hosting the Sign-In Flow — three options

What must hold in every option (the MCP conformance frame): the upstream token and PKCE verifier never leave the credential holder; per-user credential isolation; the harness speaks only standard OAuth2/MCP; DIAL authorization applies to every call. The options differ in where the sign-in orchestration lives — and therefore in trust boundaries, release cadence, and product alignment.

Separate service as-is · proven

A small OAuth2 AS + federation orchestrator beside the front door; Core trusts it as an extra identity provider (config-only).

  • +Zero Core changes — works on today's Core, adoptable by any deployment by config; already field-proven on real harnesses
  • +Small, single-purpose, fully threat-modeled trust surface; independent release cadence
  • +IdP-agnostic and Core-version-agnostic; the executable spec for any future Core-native work
  • −One more always-on component (a signed-off deviation) and a Tier-0 signing key outside Core's custody
  • −Per-toolset audience binding is structurally unavailable; a leaked token is valid deployment-wide for its lifetime
  • −The 401-challenge rewrite lives in the router — a workaround for Core's own inverted challenge
Choose whendeploying now, on unmodified Core, without waiting for a product release.

Inside DIAL Core strategic

Core natively answers the sign-in: its own OAuth surface per toolset, federation built in, tokens minted by Core itself.

  • +One component; the extra-IdP machinery and the second Tier-0 key disappear — Core's own token custody covers it
  • +The no-credential 401 is answered at the source (the router workaround retires) and per-toolset audience binding becomes possible
  • +Product-aligned: every DIAL deployment gets it; the PoC's design, threat model, and harness measurements are the spec
  • −A Core code change (Java port of AS + federation + SSRF controls) on Core's release cycle — the PoC exists because waiting was not viable
  • −The public OAuth surface moves INSIDE the credential holder — a Core flaw's blast radius grows to every stored credential; the hardening bar rises
  • −Deployments on older Core versions still need the external gateway as a bridge
Choose whenthe capability should ship with DIAL itself; use the gateway as the bridge and the specification until then.

Keycloak extension IdP-bound

The harness does OAuth against Keycloak directly; a custom extension orchestrates the upstream consent mid-login and hands Core the code.

  • +The harness token IS a Keycloak token — Core needs no extra IdP entry, same trust simplification as the Core option
  • +SSO, session and consent management are native; no separate AS to build or operate
  • −Deep SPI surgery: a mid-login browser redirect to the upstream and back is outside Keycloak's extension model; the broker's challenge/client semantics do not match Core's verifier binding
  • −Couples the IdP to MCP concepts and ties the solution to Keycloak specifically — the design is otherwise IdP-agnostic
  • −Same release-cadence and upgrade-fragility problems as the Core option, in a less standard extension surface; still needs the upstream client re-registration story
Choose whenKeycloak is guaranteed forever, the deployment owns its realm config, and the verifier-binding obstacle is solved — otherwise it inherits the Core option's costs with a narrower future.

DIAL Chat fails the premise

Chat hosts the harness-facing sign-in: its existing DIAL session is the identity leg, and its toolset sign-in UX already drives the upstream consent.

  • +The most silent flow of all options — the user's DIAL session is already there; no identity round-trip at all
  • +The sign-in UX already exists (Chat drives the same consent + /signin choreography today); no new component
  • −FAILS THE PREMISE: the project exists for deployments where Chat is NOT installed — hosting here makes Chat mandatory again
  • −A Tier-0 signing key inside a user-facing frontend product — the weakest custody of any option
  • −Couples the flow to one chat frontend; the DIAL ecosystem has several, and the harness-facing AS is backend work in a UI product
Verdictdominated: where Chat exists its own flow already works; where it doesn't, this option can't help. Keep Chat as a consumer of the same credential store, not the host.
Recommendation: ship the separate service now (proven, config-only), and take the Core-native sign-in AS upstream as the strategic direction — the gateway is its executable specification and remains the bridge for deployments on older Cores. The Keycloak extension is worth revisiting only with Keycloak guaranteed and the verifier-binding obstacle solved. Shared regardless: MCP authorization conformance, credential containment, per-user isolation, and the audit trail are properties of the design, not of the hosting — they port to whichever option wins. The widening use case: with this gateway as the harness-facing AS, the deployment's IdP no longer needs any MCP compliance — the gateway consumes its incompliances (no CIMD/DCR, quirky claims/scopes) and represents a perfectly MCP-compliant AS for the whole harness ecosystem, for toolsets and for apps with MCP endpoints alike. Whoever hosts the flow hosts the deployment's entire harness-authN path — which raises the bar on HA and key custody for every option.
